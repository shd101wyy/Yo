## §1 The framing bug (the one that matters)

Measured against the installed v0.2.45 Windows binary, the reply to
`initialize` starts:

```
Content-Length: 459\r\r\n\r\r\n{"jsonrpc":"2.0",...
```

`write_lsp_message` (`src/lsp/transport.yo`) prints an explicit `\r\n\r\n`
through libc stdio, and the MSVC CRT's stdout defaults to **text mode**, where
every `\n` is translated to `\r\n` — each `\r\n` becomes `\r\r\n`. The
spec's base protocol terminates the header block with exactly `\r\n\r\n`;
vscode-jsonrpc's `tryReadHeaders` state machine (states CR→CRLF→CRLF CR→CRLF
CRLF) never reaches its terminal state on `\r\r\n\r\r\n` and keeps buffering
forever, so the client's `initialize` future never resolves. Verified against
`vscode-languageserver-node`'s `MessageBuffer.tryReadHeaders` source, and
empirically: a Python driver with a conforming parser receives nothing at all.

Input is unaffected: `read_lsp_message` reads through `BufReader(Stdin)`,
whose path is the async runtime's raw `read` (`std/io/stdio.yo`), not libc
FILE\* — no translation. Only output framing is broken.

**Fix** (opening as PR #2 of this series): put stdout in binary mode once at
server startup on Windows, following the established windows-helper shape in
`src/main.yo` (`{ GlobalMemoryStatusEx } :: c_include("<windows.h>", …)`):

```rust
_setmode(_fileno(stdout), _O_BINARY);
```

via a function-local `c_include("<io.h>", _setmode : …, _fileno : …)` —
`ordered_c_includes` (`src/codegen/c/collection.yo`) already hoists
`<windows.h>` first and filters `<io.h>` out on non-Windows targets, so the
Linux/macOS builds are untouched. No golden changes on Linux (behavior there
is byte-identical to today).

**Why nothing caught it** (three independent blind spots, worth fixing as part
of the same plan — see §6):

1. No CI leg drives a Windows `yo lsp` over a pipe. `test.yml` runs on
   `ubuntu-latest` only; the release workflow's Windows legs compile and
   smoke-test the bundle (PE headers, allocator literals, a compile) but never
   open an LSP session.
2. The lsp cli-cases goldens were recorded on Linux/macOS developer machines;
   `refit_lsp_frames` in `scripts/cli-diff-test.sh` matches `(\r?\n\r?\n)`,
   which cannot match `\r\r\n\r\r\n` — run on Windows those cases would score
   GOLDEN-DIFF (frames not refit), so the harness today would notice, but only
   if someone ran it there.
3. Real-client interop was only ever exercised by humans on macOS/Linux.

## §2 Verified smaller defects (fix sketches)

Each has a full reproduction in its issue doc; sketches here for sequencing.

- **Rename validation** (S2): `handle_rename` only rejects an empty
  `newName`. Validate by lexing: `tokenize(new_name)` must yield exactly one
  Identifier token covering the whole string, and the name must not be
  `is_reserved_builtin_binding_name` / `is_reserved_operator_name`
  (`src/token.yo` exports both). Answer a JSON-RPC error (the `RequestFailed`
  family, code 0) with a message naming the rule — clients surface it in the
  rename input box. While there, advertise `renameProvider` as
  `{ prepareProvider : true }` and implement `textDocument/prepareRename`
  (return the identifier range at the cursor; members/labels answer nothing) —
  VS Code then only opens the input box on renameable symbols.
- **`includeDeclaration`** (S3): read `params.context.includeDeclaration` in
  the dispatch and pass it to `handle_references`; when false, drop the
  occurrence that sits on the declaration token (`collect_symbol_occurrences`
  already knows it — it is the `_binding_token_of` result).
- **`$/` requests + lifecycle** (S3): in `_handle_message`, answer `$/`-prefixed
  REQUESTS with `-32601` (notifications stay ignored); before `initialize`,
  answer requests (other than `initialize` itself) with `-32002`
  (ServerNotInitialized); after `shutdown`, answer any request with
  `-32600` (InvalidRequest). Three arms in one place, no feature changes.
- **Formatting range** (S3): end the whole-document edit at the last line's
  end instead of `(line_count, 0)` — `lines.get(line_count - 1)`'s rune count.
  (VS Code clamps out-of-bounds ranges; other clients are entitled to reject
  the edit.)
- **documentSymbol** (S3): also walk top-level `=` statements whose left side
  is a `name : T` pair (the `(x : T) = value` typed-declaration form every
  module in `src/` uses for mutable module constants) and emit a Variable
  symbol for the name atom. Keeping `range == selectionRange` (name token) is
  fine for now; note it as a known cosmetic limitation rather than computing
  subtree end positions.

## §3 Missing features, ranked

Not bugs — the capability list in `_initialize_result` is honest. Ranked by
(user value × how much existing machinery they reuse):

1. **`textDocument/documentHighlight`** — trivial: `handle_references` minus
   the `includeDeclaration` question, same file, `DocumentHighlight` items
   with `kind` (read/write/text). VS Code's selection-highlight currently
   falls back to word matching, which is exactly the spelling-match mistake
   `references` was fixed to avoid.
2. **`textDocument/prepareRename`** — with §2's rename validation; tiny.
3. **`textDocument/typeDefinition`** — hover already resolves the expr's type
   and `definition.yo` already resolves a type's declaration token
   (`_type_decl_token`); glue them.
4. **`workspace/symbol`** — iterate open documents' symbols (§2 fix) plus the
   module cache; even open-docs-only would be useful. Ranked below 3 because
   it wants an index shape decision (see §5 of
   `plans/archive/LSP_IMPLEMENTATION.md`, which listed it as future work).
5. **`textDocument/semanticTokens`** — the lexer + `classify_atom_roles`
   give a cheap token pass (keyword/operator/literal/type/field/variant/
   function-by-ExprInfo). Full fidelity wants the ExprInfo walk; a syntactic
   first cut is a real improvement over the TextMate grammar (which cannot
   know types or members).
6. **Diagnostics `relatedInformation`** — the typed channel already carries
   the note/help children of an error; today they surface as separate 0:0
   entries when they point elsewhere. Wiring them as `relatedInformation` on
   the primary diagnostic puts them in the Problems panel with working links.
7. **`codeAction` `context.only` filtering** — ignore `only` today; one filter
   clause when a second action kind ever exists.

Deliberately NOT proposed: inlay hints (the attic shipped them disabled —
`plans/archive/P4_LSP.md` slice 5; revisit only with a different hint style);
code lens (needs a test-runner protocol decision); incremental sync (full sync
is fine; the cost is the analysis, not the text transfer).

## §4 Observations recorded here, not filed

- **Cross-file rename/references are same-file only** — documented behavior
  (`docs/en-US/LSP.md` §6); becoming cross-file is a design question (which
  files to re-analyze, and the S1 fix has to land first for it to matter on
  Windows anyway).
- **Hover at a token's end column answers null** (`_find_token_at` requires
  `character < start + width`); cursor-at-end-of-word is a common keyboard
  position. One-line inclusive-bound change, but it shifts every feature's
  matching; fold into whichever §3 item lands first.
- **`serverInfo` carries no `version`** — deliberate (golden churn); recorded
  in `server.yo`.
- **The cli-case harness masks framing defects** (`refit_lsp_frames` rewrites
  `Content-Length` and tolerates `\r?\n\r?\n`) — fine for its purpose (the
  body is the review surface), which is why §6 proposes a strict-framing
  smoke driver as the Windows gate instead.

## §5 What is already right (so a future audit does not re-litigate)

Position encoding (UTF-16/UTF-32 negotiation, rune↔UTF-16↔byte conversions),
percent-encoded `file:` URI round-trips including the Windows drive spellings,
last-parsed-outcome retention for mid-edit requests, binding-identity
references/rename (the member/label atom-role classification), diagnostics
severity/code/repair plumbing into quickfixes, and import-path/import-list/
dot/enum-prefix completion modes — each of these has a fixed issue doc behind
it (`issues/fixed/lsp-*.md`, 13 docs) and live tests; none regressed in this
audit's probes.

## §6 Test-infrastructure plan (making the blind spot visible)

1. **A strict-framing handshake script** (`scripts/lsp-strict-handshake.py` or
   equivalent): spawn the binary, run `initialize`/`initialized`/`didOpen`/
   `shutdown`/`exit`, assert EVERY outgoing frame is exactly
   `Content-Length: N\r\n\r\n` + N body bytes with a conforming parser (the
   vscode-jsonrpc state machine, not a tolerant readline). Fails on Windows
   today; passes on Linux; runnable anywhere in seconds. That script is the
   regression test for finding 1 and the seed of any future cross-platform
   LSP smoke job.
2. **A Windows CI leg that runs it** — smallest useful step is adding the
   script to the release workflow's existing `windows-latest` /
   `windows-11-arm` smoke steps (no new job); a full windows test matrix is a
   separate decision (runner minutes).
3. Optionally, an `opts` flag for lsp cli-cases that asserts strict framing on
   the recorded stream instead of refitting headers.
