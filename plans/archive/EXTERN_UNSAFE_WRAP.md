# Extern Call-Site `unsafe(...)` Wrap

Status: **✅ Landed.** All phases complete (A gate, B tests, C migration, D unsafe-report granularity, E docs). Verdicts pinned in `tests/extern_unsafe_wrap.test.yo`; classification covered by `src/tests/unsafe-report-classify.test.ts`.

## Problem

Currently a file declaring `pragma(Pragma.AllowUnsafe);` can call any
`extern "c"` function with no syntactic marker at the call site:

```rust
pragma(Pragma.AllowUnsafe);
c_include("<stdlib.h>", malloc : (fn(size : usize) -> ?*(void)), ...);

allocate :: (fn(n : usize) -> ?*(void))(malloc(n));  // no marker
```

The pragma is a **file-level** pass: once declared, every line in
the file is implicitly allowed to call C, dereference raw pointers,
construct raw pointer types, etc. The reader has no way to tell at a
glance which expressions are UB-capable and which are pure Yo.

This is Known Limitation #2 in `plans/MEMORY_SAFETY.md`:

> Calling a C function with the wrong argument types is UB, but a
> call site like `c_function(x, y, z)` carries no syntactic marker —
> the only opt-in is the file's `pragma(Pragma.AllowUnsafe);`.

The pragma's coarseness is fine for `unsafe(...)`-wrappable
operations (`.*` deref, `&+` arithmetic, `consume(p.* = v)`) — those
already have the wrap as the per-site marker, and the pragma is
just the file-level gate on `unsafe(...)` itself. But extern calls
have no parallel wrap requirement today, so the pragma ends up
double-duty: file-level gate AND per-site authorization.

## Goal

Require **every `extern "c"` call site to be wrapped in `unsafe(...)`,
even in privileged (pragma'd) files.** This makes:

1. `yo unsafe-report` line up exactly with UB-capable lines (currently
   it lists the file but not the specific lines).
2. Reviewers see a per-call marker matching Rust's `unsafe { c_call(...) }`.
3. Pure-Yo code in a privileged file (utility functions, stdlib
   wrappers' inner logic) stays visually unmarked, isolating the
   FFI calls.

## Non-Goals

- **No change to `extern(...)` declaration blocks.** Declarations are
  static — they don't execute. The pragma is the right gate for
  declaring (and importing) extern symbols.
- **No change to `c_include(...)` declarations.** Same reasoning.
- **No change to `asm(...)` blocks.** The `asm` keyword is itself the
  per-site marker (parallel to `unsafe(...)`), and the pragma gates
  who can write it. Wrapping `unsafe(asm(...))` would double-mark.
- **No change to `unsafe(...)`'s own semantics.** It already exists as
  a transparent compile-time marker; we just expand what it gates.
- **No change to the pragma model.** Pragma still required to declare
  / call externs (existing gate) AND `unsafe(...)` now also required
  at the call site (new gate). The two are additive, not alternative.
- **No call-graph propagation.** Calling a function whose body calls
  an extern does NOT require `unsafe(...)` at the caller. The
  body-author wrapped the extern; the wrapper function itself is now
  safely callable. Matches Rust's `unsafe fn` vs. `fn` distinction:
  Yo doesn't have `unsafe fn`, but the wrapping pattern is the same.

## Design

### Detecting an extern call site

A function call is an extern call site iff the resolved callee's
`FunctionType` has `isExtern === "c"` (the existing type-level
marker set by `extern(...)` / `c_include(...)` declarations in
`src/evaluator/exprs/extern.ts` and `src/evaluator/exprs/c-include.ts`).

This catches:

- Direct calls: `malloc(usize(64))`.
- Calls through a variable holding the extern function value:
  `f := malloc; f(usize(64))`.
- Method-style calls if any FFI declarations grow methods (none
  exist today, but the check is shape-agnostic).

It does NOT catch:

- Calls to a Yo function that internally calls externs (correct —
  the wrap is the body author's responsibility, not the caller's).
- Function pointers stored in a struct whose field type lost
  the `isExtern` marker through type erasure. If we hit such a
  case, the type system already requires the field type to carry
  `isExtern` (it's part of FunctionType), so this shouldn't happen
  for direct stores.

### The gate

In the call evaluator (`src/evaluator/calls/...`), after resolving
the callee's FunctionType:

```typescript
if (
  calleeType.isExtern === "c" &&
  !context.unsafeContext &&
  !isAutoGeneratedExpansion(expr.token.modulePath)
) {
  throw formatErrorMessage({ ... });
}
```

Two exemptions:

1. **`context.unsafeContext === true`** — the call is lexically
   inside an `unsafe(...)` wrapper. This is the intended escape
   hatch. The existing `evaluateUnsafe` already sets this flag.
2. **`isAutoGeneratedExpansion(modulePath)`** — the call site's
   module URI starts with `auto-generated://` (macros, derive
   expansions, prelude desugarings). These inherit privilege from
   the call site that triggered the expansion; requiring the
   user's expansion site to wrap each macro-generated extern call
   in `unsafe(...)` would be hostile to the macro author. Mirrors
   the existing `isImplicitlyUnsafeCapableFile` treatment of
   `auto-generated://`.

Note: the pragma file-level gate is NOT re-checked here. By the
time we reach this point, the extern declaration itself was
admitted only because the _declaring_ file had the pragma; that's
sufficient evidence that someone with privilege brought the symbol
in scope. The new gate is about per-call-site review, not
declaration privilege.

### Diagnostic

```
error: Call to extern "c" function 'malloc' must be wrapped in
'unsafe(...)' to mark the call site as audit-capable.

C functions are outside Yo's type-checking reach. Wrong argument
types, contract violations, or aliasing assumptions can produce
undefined behavior. Wrapping each call site lets `yo unsafe-report`
flag exactly where the UB-capable operations live, instead of just
noting that the whole file is privileged.

  -> at allocate, line 5, expression `malloc(n)`

Fix: wrap the call:

  unsafe(malloc(n))
```

### Where the gate fires

In `src/evaluator/calls/_call.ts` (or wherever the main function-call
evaluator dispatches), after resolving the callee's `FunctionType` and
before evaluating arguments. The unsafe-context flag is already
threaded through `EvaluatorContext.unsafeContext`.

### Migration

Audit all `pragma(Pragma.AllowUnsafe);`-bearing files (`std/`,
`yo-self/`, `tests/`, plus any user files). Every line that calls an
`extern "c"` function — typically `__yo_*(...)`, libc names from
`std/libc/*`, or symbols introduced via `c_include(...)` — needs to
be wrapped in `unsafe(...)`.

Rough scale:

- `grep -rE "__yo_[a-z_]+\(" std/ | wc -l` returns ~843 references
  (includes doc comments, imports, etc. — actual call sites likely
  ~500–700).
- libc wrappers in `std/libc/*.yo` are mostly one-line passthrough
  functions; each gets one `unsafe(...)` wrap.
- `std/sys/*.yo` files have heavier mixes — wrap per call site.

Approach: a `scripts/wrap-extern-calls.ts` AST-pass that:

1. Loads each `.yo` file with `pragma(Pragma.AllowUnsafe);`.
2. Walks the AST; for each function call whose callee resolves to
   `isExtern === "c"`, wraps the call in `unsafe(...)`.
3. Idempotent — skips calls already inside an `unsafe(...)`.
4. Runs `./yo-cli fmt` on the result.

A manual pass first (touch one or two stdlib files by hand) lets us
verify the diagnostic and codegen before bulk migration.

### What the diff looks like

Before:

```rust
malloc :: (fn(n : usize) -> ?*(void))(__yo_malloc(n));
```

After:

```rust
malloc :: (fn(n : usize) -> ?*(void))(unsafe(__yo_malloc(n)));
```

Or, more realistically for `std/libc/stdlib.yo`-style passthroughs,
the wrap goes inside the body:

```rust
// before
free :: (fn(p : *(void)) -> unit)(__yo_free(p));
// after
free :: (fn(p : *(void)) -> unit)(unsafe(__yo_free(p)));
```

Note the wrapper function `free` is still a normal `fn(...)`; only
its body's extern call is wrapped. Callers of `free` from outside
the file (or from safe code, if exposed) don't need `unsafe(...)` —
the wrapper's body owns the audit obligation.

## Phases

### Phase A — Detect extern calls in the evaluator

- Find the main function-call evaluator (likely
  `src/evaluator/calls/_call.ts` or similar).
- After resolving the callee's `FunctionType`, check `isExtern ===
"c"`. If so AND `!context.unsafeContext` AND not auto-generated,
  reject with the diagnostic above.
- Confirm the gate doesn't fire on:
  - Calls to Yo functions whose bodies call externs (the body owns
    the wrap, not the caller).
  - Calls to extern functions inside an `unsafe(...)` wrapper.
  - Calls in `auto-generated://` URIs (macro expansions).

### Phase B — Unit / integration tests

- Add `tests/extern_unsafe_wrap.test.yo`:
  - `comptime_expect_error` for an unwrapped extern call in a
    pragma'd file (proves the gate fires even with the pragma).
  - Positive: wrapped extern call compiles and runs.
  - Positive: a Yo wrapper whose body wraps the extern is callable
    without `unsafe(...)` at the caller.
- A `src/tests/extern-unsafe-wrap.test.ts` style test if AST-level
  unit testing is more natural (parallel to
  `type-representation-pointer.test.ts`).

### Phase C — Stdlib migration

- Write `scripts/wrap-extern-calls.ts`.
- Dry-run, eyeball the diff for the first few files.
- Bulk apply to `std/`, then `yo-self/`, then `tests/`.
- Run `./yo-cli check ./std` and `./yo-cli test --bail` to
  validate.
- One mechanical commit (parallel to the
  `scripts/add-pragma.ts`-driven Phase C of MEMORY_SAFETY in scale).

### Phase D — `yo unsafe-report` granularity ✅

- `src/unsafe-report.ts` classifies every `unsafe(...)` finding into
  one of five sub-kinds: `extern-call` (callee name recorded),
  `deref`, `arith`, `addr-of`, `other`. A first pass harvests every
  extern "c" function name declared via `c_include(...)` or
  `extern("c", ...)`; the per-line scanner uses the set to
  recognize extern callees.
- Output adds a per-sub-kind tally and a "Top extern callees" table
  (descending by call-site count, top 15 shown). Each finding line
  now reads `unsafe(extern-call:strlen)` / `unsafe(deref)` / etc.,
  so a grep on the report tells the auditor exactly what each wrap
  is guarding.
- Coverage in `src/tests/unsafe-report-classify.test.ts` (7 tests).

### Phase E — Docs

- Update `plans/MEMORY_SAFETY.md` Known Limitation #2: mark
  RESOLVED with a pointer to this doc.
- Update `.github/instructions/yo-design.instructions.md`: brief

- `docs/{en-US,zh-CN}/DESIGN.md`: update if there's a section on

## Open Questions

1. **What about `extern "yo"` functions?** Yo can declare functions
   with `extern "yo"` to give them an explicit ABI / symbol name
   without C-FFI semantics. They're not UB-capable in the C-contract
   sense. Decision: gate fires only on `isExtern === "c"`, leaving
   `extern "yo"` untouched. If we later add other languages
   (`extern "rust"`, etc.), evaluate per language.

2. **Method calls through traits.** If a trait method's implementation
   is itself an extern call, does the trait-method dispatch hide the
   extern-ness from the gate? Today no trait methods are direct
   externs (they wrap externs at most), so this should not arise.
   Re-verify during Phase A by grepping for `extern` inside `impl(...)`
   blocks. If a case exists, the gate's `calleeType.isExtern` check
   will still see through the dispatch because the resolved
   FunctionType still carries the marker.

3. **Variadic extern functions (`printf`-style).** The variadic
   parameter is still part of the FunctionType; `isExtern` is on the
   FunctionType itself, so the gate catches these too. No special
   case needed.

4. **`extern(...)` blocks declaring `Type` aliases.** A non-function
   field like `libc_FILE : Type` carries `isExtern === "c"` on the
   type, but it's never called. The gate only fires on call expressions,
   so type-only extern bindings are unaffected.

5. **`yo-self/` bootstrap migration.** The self-hosted compiler in
   `yo-self/` calls many `__yo_*` externs. The Phase C script applies
   uniformly to all pragma'd files, so this gets covered.

6. **CTFE evaluator and macros.** Some `__yo_*` builtins are called
   from inside compile-time machinery (derives, builtin macros).
   These are typically auto-generated, so the
   `isAutoGeneratedExpansion` exemption covers them. Verify
   during Phase B by running the full test suite — any uncaught
   call from a non-auto-generated path will surface.

## Risk Assessment

- **Migration noise.** ~500–700 call sites get a 9-character wrap
  each. One big mechanical commit. Reviewable by spot-checking a
  handful of files.
- **Macro / derive expansions.** The auto-generated bypass handles
  most cases. Any leaks will surface as test failures, easy to
  diagnose.
- **Performance.** `unsafe(...)` is a transparent compile-time
  marker — no runtime cost. Codegen unchanged.
- **Reader hostility.** A pragma'd file now has visual noise in
  every FFI line. Mitigation: the wrap is the point — that noise
  IS the per-site review marker. Stdlib readers should expect
  density.
