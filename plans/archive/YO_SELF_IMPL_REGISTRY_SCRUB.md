**Status: RESEARCHED AND ADVERSARIALLY VERIFIED 2026-08-15 — NOT IMPLEMENTED.**

agent synthesized the plan below; three independent adversarial verifiers
(TS-claims lens, yo-self-claims lens, design-soundness lens) then re-opened
every cited `file:line` and attacked the design. All three returned
**sound-with-fixes** — the corrections are in the next section and they
**override** anything contradicting them below.

Facts I then re-verified myself, by hand, because the whole plan rests on
them (all confirmed):

- `clear_impls_from_module`, `clear_generic_impls_from_module` and
  `clear_all_global_impl_state` are literal no-op stubs —
  `(fn(_module_path : String) -> unit)(())` — at
  `yo-self/evaluator/index.yo:295-302`, and grep finds **zero callers**
  anywhere outside that file. Their own comment says callers "can safely

- `mm_reset` (`yo-self/module_manager.yo:249-260`) clears the module cache,

## CORRECTIONS — these override the plan text below

**1. The anonymity predicate must key off `trait_key`, not the trait NAME.**
All three verifiers flagged this independently. The plan's
`_type_name_for_doc(entry.trait_type).len() == 0` is not TS's
`!genericImpl.traitType.typeName`: TS stamps a `typeName` on every
comptime-fn-returned type (`src/evaluator/calls/comptime-fn.ts:261-265`), so
`Eq(Box(T))`, `Iterator(…)`, `Ord(…)` are correctly EXCLUDED from its
duplicate scan — whereas yo-self leaves every trait literal's name empty
(`trait.yo:1108`), so the name-based test would classify real parameterized
traits as anonymous and **reject valid std impls**. Use
`entry.trait_key.len() == usize(0)` instead: inherent entries are built with
`t_unit()` → empty key (`impl.yo:3152-3153`), while trait entries always get
a non-empty key from `get_base_trait_key` (`impl.yo:3104`). Apply to both the
incoming-entry gate and the per-existing-entry skip.

**2. The concrete-duplicate pin must cross a module boundary.** Two verifiers
showed the proposed single-file fixture is **not red on the TS arm**, so it
would pin nothing: TS's flatten takes the REPLACE branch whenever the
incoming and existing rows share a module path
(`src/evaluator/values/impl.ts:2875-2881`), and two impl blocks in one file
always do. Only a cross-module duplicate reaches the throw at
`impl.ts:2883-2889` — e.g. `main.yo` and an imported `dep.yo` each declaring
an inherent `impl(str, foo : …)`, or `main.yo` redefining an inherent method
the prelude already registers on `str`. The GENERIC fixture may stay
single-file: `registerGenericImpl` (`impl.ts:1074-1114`) has no
module-identity exemption and throws regardless of module.

**3. Hoist the check above the supersede loop.** The plan's chosen site
(`impl.yo:3677-3728`) is unreachable for the shape it targets, because the
pre-pass registers a forward shell for EVERY direct `name : (fn(…) -> R)(body)`
field into the REAL table with no dedup (`_try_create_forward_shell`,
`impl.yo:2207-2250`, registered at `impl.yo:3303`). Put the violation check
immediately after `existing_entries := get_type_trait_methods_by_name(...)`
at `impl.yo:3644`, BEFORE the supersede loop, so both branches are covered —
and there the `__forward_shell` skip genuinely matters, reproducing TS's
throwaway-clone invisibility. The same-module REPLACE must also remove the
pre-existing row on the supersede path.

## Port plan (researched 2026-08-15)

What is being ported is the _rejection_ half of TS's impl-registration machinery: the duplicate-method scan inside `registerGenericImpl` (src/evaluator/values/impl.ts:1074-1114), the replace-or-reject branch of the direct-impl flatten (impl.ts:2865-2892), the named-trait `checkDuplicateImpl`/`registerImplForType` pair (impl.ts:1129-1153, 1158-1182), and the per-module scrub functions that make those checks survivable across re-evaluation (`clearImplsFromModule` impl.ts:2753-2769, `clearGenericImplsFromModule` impl.ts:982-995, `clearAllGlobalImplState` impl.ts:1018-1035). The reason to port them is not that a shipped path re-registers today â it does not, per the "Why it is currently unreachable" section above â but that the two compilers fail in categorically different ways when one ever does. TS dies at the registration site with `Method "len" is already defined for type "comptime_str"` (impl.ts:1101-1107, 2883-2889); yo-self's `register_generic_impl` (yo-self/evaluator/values/impl.yo:344-378) appends unconditionally and `register_type_trait_method` (yo-self/evaluator/values/type_trait_methods.yo:161-175) appends unconditionally, so the second registration silently doubles the registry and the damage surfaces later, in another file, as a method-resolution miss â and because codegen's missing-`ExprInfo` path emits an in-band `// Failed to transpile` comment instead of halting (yo-self/codegen/exprs/generation.yo:544-575), the corrupted build can still exit 0. Every check below is therefore a _loud error at the cause_, and every scrub below is what keeps that loud error from becoming a false positive.

The single structural prerequisite is module attribution: TS carries it in four places (`implRegistry` keyed by module path, impl.ts:265; `TraitField.sourceModulePath`, src/types/definitions.ts:357-360; `GenericImpl.sourceModulePath`, impl.ts:352-354; `ImplRecord.modulePath`, impl.ts:970-976) and yo-self carries it in none â the identifier `source_module` does not occur anywhere under `yo-self/`. The channel, however, already exists and is already correct: `ctx.current_module_path` (yo-self/evaluator/context.yo:263-264) is populated by `eval_context_new` (context.yo:351) with the very same `abs` string that keys the module cache and stamps every token's `module_path` (yo-self/module_manager.yo:315, 324, 326). It is currently a dead field â the only non-declaration hits are one copy-forward (yo-self/evaluator/calls/function_type.yo:192) and a unit test â so this port is its first consumer.

### Step-by-step port

**Step 1 â `source_module_path` on `GenericImplEntry`.** Add a twelfth field `source_module_path : String` to the struct at impl.yo:173-203 (`""` = TS's `undefined`, matching the existing `constructor_func_id : String` ""-means-unknown idiom on `Struct`). Construction is positional at all three sites, so append it last and keep the existing numbered comments intact: impl.yo:2788 (negative generic), impl.yo:3103 (Case-2 trait impl), impl.yo:3154 (Case-2 inherent impl). Fill from the context, not the token: `match(ctx.current_module_path, .Some(p) => p.clone(), .None => String.new())`. This is TS's channel in TS's place â both TS registration sites read `context.currentModulePath` (impl.ts:3286 for the structural branch, impl.ts:3291 for the attach branch, and the same field on the generic entry built just above `registerGenericImpl` at impl.ts:3699). Do **not** substitute `ast_expr_token(expr).module_path`; the lexical-token preference in TS is a _type-definition_ rule (src/evaluator/types/struct.ts:65-76), not an impl rule, and using it here would attribute a derive-expanded impl to `auto-generated://â¦` (yo-self/parser.yo mints that URI; it is detected by `is_implicitly_unsafe_capable_file`, used at impl.yo:3393).

**Step 2 â `source_module_path` on `MethodEntry`.** Add the field to the `ref(struct(...))` at type_trait_methods.yo:146-155 and update its file header (type_trait_methods.yo:17-26 enumerates the mirrored TS `TraitField` members and currently omits `sourceModulePath`). Every construction site uses label syntax, so the compiler will name each one: impl.yo:1094, 2297, 2900, 3044, 3506, 3703, 3875, 3954; yo-self/env.yo:3073, 3630, 3694, 3776; yo-self/evaluator/calls/trait_type.yo:341; yo-self/codegen/functions/collection.yo:1042, 1188. Fill them as follows.

- The real impl registration (impl.yo:3703) and the trait-default registration (impl.yo:3875): from `ctx.current_module_path` as in step 1.
- The shell entry (impl.yo:2297) and the provisional entries (impl.yo:2900, 3044, 3506, trait_type.yo:341): same context path where a `ctx` is in scope; these rows are either scrub-invisible (provisional table) or explicitly skipped by the dup scan (shells, step 6), so their value is diagnostic only.
- The derived assoc-type registration inside `try_match_generic_impl` (impl.yo:1092-1102) has **no** `ctx` and no `exn` (signature at impl.yo:701-707); it must inherit `entry.source_module_path`. That single site is the structural reason attribution has to live on the entry record rather than being passed as a parameter.
- `env.yo:3073/3630/3694/3776` re-materialize an existing entry (the comment at env.yo:3068-3072 says mutating the input would leak across the registry's shared references), so **copy** `m.source_module_path`, do not blank it.
- The codegen-side `trace`/`___dispose` registrations (collection.yo:1042, 1188) are not impl declarations: use `""`, mirroring TS's `undefined`. This is also what makes the scrub in step 8 sound despite those rows being keyed by `type_key(ct)` (collection.yo:1032-1041) rather than `type_id_or_empty` â a `""`-attributed row is never removed by a per-module filter.

Correction to carry into the change: `yo-self/evaluator/calls/index_trait.yo:386/421/1581` construct `_IndexMethodEntry` (declared index_trait.yo:60), a _different_ struct. They need no edit.

**Step 3 â a faithful receiver-base-id function.** Add `_receiver_base_type_id(t : TypeValue) -> String` to impl.yo mirroring impl.ts:1057-1065: `Struct` â `constructor_func_id` when non-empty, else `lookup_struct_ctor_fid(id)` (expr_info.yo:1175), else `id`; `EnumT` â `lookup_enum_cfid(id)` (yo-self/value.yo:1015) when non-empty, else `id`; `TraitT` â `lookup_trait_ctor_fid(id)` (expr_info.yo:1198), else `id`; everything else â `type_id_or_empty(t)` (type_trait_methods.yo:58-120). Do **not** reuse `_receiver_base_type_id_for_doc` (impl.yo:1655-1668) â it consults the ctor fid on the `Struct` arm only, so `Option(T)`-style enum receivers would compare by per-instantiation id and the check would silently pass. Do not "fix" the doc helper either; it has its own caller. Known fidelity limit to record in the issue: the enum cfid stamp is applied on the comptime-fn call path only (yo-self/evaluator/calls/comptime_fn.yo, and yo-self/evaluator/types/synthesizer.yo:1676-1690 documents enums minted on the fn-specialization path that bypass it), so a missing cfid degrades the check to a false **negative** (permissive), never a false positive. VERIFY before shipping: how yo-self registers `impl(Array(T,N), â¦)` at all â `type_id_or_empty` returns `""` for `.Array` (type_trait_methods.yo:118) and impl.yo has no `is_array_type`/structural branch, so TS's structural-receiver path (impl.ts:3197, 3277-3289) appears to have no yo-self counterpart; if array receivers really register nothing, the array arm of this function is dead and should be omitted rather than invented.

**Step 4 â the throw-free generic dup scan.** Add `_duplicate_generic_method_violation(entry : GenericImplEntry) -> Option(String)` to impl.yo, immediately above `register_generic_impl`. Port impl.ts:1074-1114 predicate-for-predicate, in order: (a) run only when the entry is anonymous â in yo-self that is `_type_name_for_doc(entry.trait_type).len() == usize(0)` (impl.yo:1671-1680), which is `""` for the inherent entry's `t_unit()` trait (impl.yo:3152) and non-empty for the Case-2 trait entry (impl.yo:3103-3104); (b) collect `entry.field_names[i]` where the name is non-empty and `is_function_type(entry.field_types[i])`, bail when empty; (c) compute `_receiver_base_type_id(entry.receiver_type_pattern)` and bail when it is `""` (TS's `if (receiverBaseId)` is falsy for `""` too); (d) walk **every** bucket of `g_impl_registry_keys`/`g_impl_registry_entry_lists`, skipping entries whose `_type_name_for_doc(trait_type)` is non-empty and entries whose base id differs; (e) on a label collision return the message built exactly as impl.ts:1101-1107, using `type_to_string(entry.receiver_type_pattern)` (already imported at impl.yo:71). All loops must be flag-guarded `while`s â the registry loops carry an explicit prohibition on `continue` (impl.yo:1338-1341, citing issues/codegen-continue-in-while-heap-corruption.md). No self-exclusion is needed because the push happens after the check.

**Step 5 â raise it from the evaluator frame.** The check cannot throw where TS throws. `register_generic_impl` receives only the entry (impl.yo:344) â no `exn` â and a throw from inside a helper has been observed inert under the def-time trial exn chain, which is exactly why `_enforce_loop_invariant_placement` returns the offending node and `evaluate_while` throws from its own frame (yo-self/evaluator/exprs/while.yo:97-106, 290-300); effect handlers are additionally capture-free and can never reach an enclosing `exn` (yo-self/types/flowability.yo:51-57, 1010-1015). The established shape is the `CheckSelfConstraintsFn -> Option(String)` hook whose doc says "the caller throws with its own token/exn" (impl.yo:260-267) and whose raise site is impl.yo:3447-3453. So: call `_duplicate_generic_method_violation(...)` immediately before `register_generic_impl` at impl.yo:3126 and impl.yo:3177 â both are inside `evaluate_module_value`, which holds `expr`, `ctx` and a real `exn` (impl.yo:2518-2525) and whose plain `{...}` begin-blocks capture them fine â and on `.Some(msg)` do `exn.throw(dyn(format_error_message(ast_expr_token(expr), msg, false, .None)))`. Guard the call with `!(in_def_time_trial())` (yo-self/evaluator/context.yo:790-803, imported at impl.yo:80, precedent at impl.yo:1062) so a trial can neither swallow a real violation nor manufacture a spurious one. Do **not** call it at impl.yo:2788: that entry goes to `register_negative_generic_impl`, and TS's negative path never enters `registerGenericImpl`.

**Step 6 â replace-or-reject on the concrete path.** The site is the fresh-registration branch at impl.yo:3677-3728, which already has `existing_entries := get_type_trait_methods_by_name(receiver_type_id, method_name)` in hand from the shell-supersede loop (impl.yo:3644). Port impl.ts:2865-2892: consider only rows with a non-empty label and `is_function_type(entry.ty)`; **skip rows tagged `source_trait_id == "__forward_shell"`** (the tag is set at impl.yo:2297's shell construction and tested at impl.yo:3650), because yo-self registers shells into the real table (impl.yo:3303) whereas TS keeps them on a throwaway clone of `receiverType.trait` that is restored before the check runs (impl.ts:612-619, 897-900) â the skip is TS's invisibility reproduced, not a heuristic. On a hit: if the incoming module path is non-empty **and** string-equal to the existing row's `source_module_path`, remove that one row and proceed with the push (TS's identity filter, impl.ts:2879-2881); otherwise return the violation text of impl.ts:2883-2889 and throw it from the frame as in step 5, with `ast_expr_token(expr)`.

Two sub-decisions this step must make explicitly, because TS separates by field _shape_ and yo-self has no label-`""` row. First, scope: run the flatten check only for inherent methods (`current_trait_ty` is `.None`, i.e. the incoming `source_trait_id` is `""` per impl.yo:3714-3718) and compare only against existing rows whose `source_trait_id` is `""`. That reproduces TS's anonymous-vs-named split and preserves the deliberate INHERENT-FIRST shadowing documented at impl.yo:3707-3713; named-trait duplicates are step 7's job. Second, removal mechanics: `get_type_trait_methods_for_type` hands back the **live** `ArrayList` (type_trait_methods.yo:178-186), so add the mutation to type_trait_methods.yo behind its own API rather than mutating a handed-out list at the call site. `ArrayList` exposes `remove(start, count?)` (std/collections/array_list.yo:288); the alternative, closer to TS reassigning the array, is a filter-rebuild written back with `_type_trait_methods.set(type_id, kept)` following the `_clear_pragma_for_module` pattern (yo-self/evaluator/memory_safety.yo:74-90). VERIFY which is safe here: whether any caller retains a bucket reference across this point â TS's holders of the old array keep stale data harmlessly because nothing holds one, while a yo-self in-place `remove` is visible to every holder.

**Step 7 â `checkDuplicateImpl` + `registerImplForType`.** Add an impl-record table beside `g_negative_impl_registry` (impl.yo:386-407) â either one `ArrayList` of a small struct (`receiver_type_id`, `trait_type_id`, `trait_type_name`, `module_path`) or parallel arrays in the existing house style. Key on the **raw** ids: `type_id_or_empty(receiver_ty)` and `get_trait_key(ctt)` (impl.yo:315-323), never `get_base_trait_key` â TS deliberately uses `receiverType.id` and `traitType.id` here (impl.ts:1141, 1144) so that `Eq(i32)` and `Eq(str)` do not collide, and "improving" it to the base key would reject legal code. Insert into the Case-3 named-trait region at impl.yo:3438-3465, preserving TS's order: the existing self-constraint gate first (impl.yo:3445-3457, mirroring impl.ts:3269 running before the attach at 3291), then the duplicate check (returning `Option(String)`, thrown from the frame with the text of impl.ts:1146-1151), then TS's negative-impl contradiction check (impl.ts:2837-2842 â VERIFY whether yo-self already performs this somewhere; `has_negative_impl` exists at impl.yo:387-402 and is exported), then the record registration with `module_path` defaulting to the literal `"unknown"` when the context path is empty (impl.ts:1179), then the existing `g_register_trait_value_fn` call at impl.yo:3458-3462. Keep `currentModulePath` inert in the comparison, as TS does (the parameter is eslint-suppressed at impl.ts:1132-1133).

**Step 8 â the per-module clears, with every participating registry named.** TS's cleanup index is `implRegistry` (impl.ts:265) written by `registerImpl` only when a module path is present (impl.ts:2853-2856, 2791-2798). Port it as module path â receiver-type-id list, written from the same place in impl.yo's Case-3 path, and then fill the three stubs at yo-self/evaluator/index.yo:295-302 by delegating into impl.yo / type_trait_methods.yo (index.yo is the re-export point, not the implementation site). Participation list â a registry missing from it is a leaking scrub:

`clear_impls_from_module(module_path)` â mirror impl.ts:2753-2769: (1) `_type_trait_methods` (type_trait_methods.yo:157-158): for each touched bucket, filter-rebuild dropping rows whose `source_module_path == module_path`, writing back with `.set` (the `_clear_pragma_for_module` pattern, memory_safety.yo:74-90); (2) delete the module's key from the new touched-types index (TS's `implRegistry.delete`, impl.ts:2765); (3) cascade into the impl-record table from step 7, filtering by `module_path` and dropping emptied keys, mirroring `clearImplRecordsFromModule` (impl.ts:1001-1012). Bucket iteration is expressible: `HashMap.keys()` exists (std/collections/hash_map.yo:600-640) and is already used in yo-self (yo-self/function_value.yo:148, yo-self/evaluator/utils/closure.yo:148), which resolves the dossier's open question â a whole-map walk is available if the touched index is ever incomplete.

### Why the shared-universe follow-on is harder than the scrub

The scrub above is a data problem: add a string to two records, filter three tables, throw from the frame that owns the token. The shared-universe work that _consumes_ the scrub is a lifetime problem, and the lifetime it must fix is one TS does not have. TS stores per-expression evaluation data **on the AST node** as the optional `$` field of both node kinds (src/expr.ts:487-512), mutated in place by the evaluator, so a cached AST inherently carries its annotations and a stale-metadata state is unrepresentable. yo-self keeps the same data in a side table keyed by a process-monotonic `ExprId` (`ExprInfoTable :: newtype(data : HashMap(ExprId, ExprInfo))`, yo-self/expr_info.yo:726-753), and `run_compile` mints a fresh table per compile while the module cache and prelude env outlive it (yo-self/main.yo:1231-1237 clears both precisely to stay consistent with the new table). The demand loader's cache-hit early return sits _above_ the line that routes a module's metadata into the shared table (`if(module_cache_has(abs.clone()), { return(...) })` at yo-self/module_manager.yo:315-317 versus `ctx.expr_info_table = t` at :334), so on a second in-process compile every cached std module short-circuits and its `ExprInfo` lives only in the discarded table. Codegen's only metadata source is that table (`get_expr_info` â `expr_info_table_get`, yo-self/codegen/utils/index.yo:351-355), and a miss emits `// Failed to transpile` as an in-band degrade signal rather than halting (yo-self/codegen/exprs/generation.yo:544-575, which documents seven consumers of that string and why making it fatal was reverted) â so the failure mode is a silent hollow binary at rc 0, not an error. The comment at main.yo:1206-1230 records the measured shape of this (47 markers on a five-file string run, 59 on tests/internal, 47â18 after clearing the two easy caches) and states plainly that the clearing is defence in depth, not the fix.

The design that has to be undone is the child process per batch: `run_test` writes each batch to `.yo_selftest_batch_<fi>_<bi>.yo` and shells out to `argv(0) compile â¦ -o â¦`, hard-failing the file on a nonzero child status (yo-self/main.yo:1828-1888), justified as parity with `moduleManager = new ModuleManager()` per batch in src/test-runner.ts. That parity claim is now only half true: TS's sequential runner already runs a **run-scoped** shared universe (`const useSharedUniverse = !isWasmBuild && !isEmcc; let sharedManager = useSharedUniverse ? new ModuleManager() : undefined;`, src/test-runner.ts:1573-1574) with a per-file scrub (`scrubSharedModule` â `sharedManager.deleteModule(modulePath)`, src/test-runner.ts:267-276) and an RSS-bounded recreate. Porting that needs, beyond this scrub: a run-level table published once and never re-set while any cache that can return an evaluated AST or `FuncVal` is live (the three statements at main.yo:1231-1234 must move together, and `compile`'s standalone self-containment must be preserved behind an explicit opt-in); a single-key module delete and an import-edge graph, neither of which exists (module_loader.yo:79-91 offers only whole-cache clear, and there are no dependents/dependencies maps to walk for TS's `deleteModuleAndDependents`, src/module-manager.ts:223-247); a complete universe flush for the memory bound, since `mm_reset` today drops the shared table while leaving the specialization, func-type and impl registries populated â which is exactly the configuration that produced the 18-marker residue; and a per-batch reset of `g_fid_rtcalls`/`g_fid_specs` (yo-self/expr_info.yo:1300-1331), whose accumulated ratio decides via `fid_fully_specialized` whether a function body is emitted at all, so cross-batch accumulation drops emissions with no marker to detect it. One global explicitly resists the obvious fix: `g_specialized_fn_caches` (yo-self/evaluator/calls/helper.yo:1384-1394) documents that a shorter lifetime already caused a worse bug (per-file re-specialization minting fresh trait ids that concrete impls no longer matched), so it must keep its process lifetime â which is the argument for making the table run-scoped rather than for clearing more state. Validation, finally, cannot be pass-count-based: a batch can report passes while running nothing, so the gate has to count `// Failed to transpile` markers per batch, and `check` â already a run-scoped shared universe over one module cache (main.yo:667-676) â cannot pin any of it, because the shared table is deliberately `.None` outside codegen (module_manager.yo:329-337).
