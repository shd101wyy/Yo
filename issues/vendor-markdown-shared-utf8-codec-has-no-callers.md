# `vendor/markdown_yo` defines and exports a shared UTF-8 codec with zero callers while six files open-code the same thing

**Status:** OPEN (upstream — `vendor/markdown_yo`, submodule pinned
`9f9340f606572f049f8d568a47ef55af525cfd5d`, `v0.0.4-8-g9f9340f`). Found
2026-09-04 during the std-API-audit re-measurement of the D4 PR 9 row.
Confirmed by code reading (`grep` over the whole vendor tree, including its
tests).
**Severity:** papercut — no wrong output on its own. It matters because the
*live* copies are not all equivalent to the dead one, and the divergences are
real bugs: the dead helper returns U+FFFD for a truncated sequence where two
live copies return the lead byte's own value
(`issues/vendor-markdown-truncated-utf8-aliases-a-valid-link-label.md`), and a
third live copy omits the bounds checks entirely and over-reads the heap
(`issues/vendor-markdown-punycode-encode-reads-past-the-buffer.md`). The
duplication is what lets a decoder be wrong in one file and right in the next.

## Symptom

`vendor/markdown_yo/src/common/utils.yo` defines two helpers under a
`// UTF-8 helpers` banner and exports both:

```rust
// vendor/markdown_yo/src/common/utils.yo:130
read_utf8_codepoint :: (fn(src_ptr: *(u8), offset: i32, src_len: i32) -> i32)({ … });
// :156
utf8_byte_len :: (fn(lead: u8) -> i32)( … );
// :306
export(is_space, is_white_space, is_md_ascii_punct, is_punct_char, is_md_punct_byte,
       read_utf8_codepoint, utf8_byte_len,
       escape_html_buf, append_raw_buf, append_lit);
```

Nothing calls either one, anywhere:

```
$ grep -rn 'read_utf8_codepoint\|utf8_byte_len' vendor/markdown_yo/
vendor/markdown_yo/src/common/utils.yo:130:read_utf8_codepoint :: (fn(src_ptr: *(u8), offset: i32, src_len: i32) -> i32)({
vendor/markdown_yo/src/common/utils.yo:156:utf8_byte_len :: (fn(lead: u8) -> i32)(
vendor/markdown_yo/src/common/utils.yo:306:       read_utf8_codepoint, utf8_byte_len,
```

Three lines: the two definitions and the export. No call sites, in `src/` or in
`tests/`.

Meanwhile the tree hand-rolls the same codec six times over. Measured inventory
at the pinned commit (`grep -rn '0xC0\|0xE0\|0xF0\|0xF8' vendor/markdown_yo/src`
minus the two generated byte-table files `src/data/emoji_data.yo` and
`src/common/entities.yo`, which push literal UTF-8 bytes and are not decoders):

| file | decoder | encoder |
| --- | --- | --- |
| `src/inline/link.yo` | `:302-322` | `:379-393` |
| `src/block/reference.yo` | `:38-58` | `:139-153` |
| `src/common/punycode.yo` | `:173-190` **(unguarded — see below)** | `:143-157` |
| `src/common/normalize_link.yo` | `:181-205`, `:351-368` (lead-byte width), `:443-520` (continuation validation) | — |
| `src/common/unescape.yo` | — | `:40-55` |
| `src/renderer.yo` | — | `:90-107` |
| `src/common/utils.yo` | `:130` **(dead)** | — |

`link.yo`'s and `reference.yo`'s decoders are byte-for-byte identical to each
other, and so are their encoders. The copies are not all equivalent, though:
`punycode.yo`'s decoder has **no bounds checks at all** where the other five
guard every continuation-byte read, and that costs a heap over-read —
`issues/vendor-markdown-punycode-encode-reads-past-the-buffer.md`. That is the
strongest argument for the dedup: a guard can currently be forgotten in six
independent places.

## Root cause

The abstraction was written and then never wired up — `read_utf8_codepoint` and
`utf8_byte_len` have no revision in which they were called. Two details explain
why the copies did not adopt them, and both have to be addressed by any fix:

1. **`read_utf8_codepoint` returns only the code point.** Its own doc comment
   claims otherwise — "Returns (codepoint, byte_length) where byte_length is
   1-4" (`src/common/utils.yo:128`) — but the signature is
   `-> i32`. A caller walking a buffer needs the width to advance `p`, so it
   cannot use this helper alone.
2. **`utf8_byte_len` derives the width from the lead byte only**
   (`src/common/utils.yo:156-165`), so it does not agree with
   `read_utf8_codepoint` on a truncated sequence: the decoder falls through its
   guarded arms to `i32(0xFFFD)` (one byte's worth of meaning) while
   `utf8_byte_len` still reports 3 or 4. Pairing them overshoots the buffer end.

So the pair as written is not composable, which is presumably why five call
sites re-derived the logic in place. That re-derivation is where the divergence
crept in: `link.yo` and `reference.yo` fall back to `cp = ch_byte` on truncation
instead of U+FFFD, which is the wrong-value bug filed alongside this one.

`plans/STD_API_AUDIT_D4_PLAN.md:461` (D4 PR 9) asked for exactly this dedup, but
the row's site list is an undercount in two ways: it names four files and misses
`src/common/punycode.yo`, `src/renderer.yo` and `src/common/unescape.yo`, and it
counts no encoders at all — the same omission `#286`'s commit message called out
for `std`.

## Fix

Do this **inside the vendor**, in
`github.com/shd101wyy/markdown_yo`. Do *not* route it onto
`std/encoding/utf8.yo`:

- it would make an independent markdown library hard-depend on one Yo std
  module for a 40-line codec;
- `utf8.decode` / `decode_lossy` take an `ArrayList(u8)` while every vendor call
  site holds a raw `*(u8)` plus `i32` offsets, so the only usable entry point is
  `utf8.decode_parts(b0..b3, available, index)` (`std/encoding/utf8.yo:186-233`)
  with an `Err` → U+FFFD arm — no simpler than the local helper;
- `decode_parts` is RFC-3629 **strict** where the vendor is deliberately lax (it
  accepts `0xC0`/`0xC1` overlongs and never validates continuation bytes), so
  the switch would change behaviour across the whole fixture suite, not just on
  the truncation case.

Concretely:

1. Make the shared decoder composable — give it an out-parameter or a pair
   return so it yields **both** the code point and the bytes actually consumed,
   and fix the doc comment at `src/common/utils.yo:128` to match whatever shape
   is chosen. On a truncated or invalid sequence it must return U+FFFD with a
   consumed width of 1.
2. Add the missing sibling, `write_utf8_codepoint(out, cp)`, factored out of any
   one of the five identical encoders.
3. Point the five open-coded decoders (`link.yo`, `reference.yo`,
   `punycode.yo`, and `normalize_link.yo`'s two lead-byte-width walks) and the
   five encoders (`link.yo`, `reference.yo`, `punycode.yo`, `unescape.yo`,
   `renderer.yo`) at the two helpers. `normalize_link.yo:443-520` validates
   continuation bytes on *percent-decoded* bytes rather than decoding a buffer;
   it needs a `utf8_sequence_len(lead)` + `is_continuation(b)` pair rather than
   the full decoder — add those alongside rather than forcing it.
4. Then bump the submodule pointer in this repo and re-green the three
   site-build legs (`.github/workflows/{test,deploy-site,release}.yml`, which
   build the vendor with `YO_STD=$GITHUB_WORKSPACE/std`).

If the maintainer of `markdown_yo` does not want the refactor, the honest
alternative is to **delete** `read_utf8_codepoint` and `utf8_byte_len` and their
export line, so the tree stops advertising a shared codec it does not use — but
that leaves the truncation bug duplicated in two files, so option 1-3 is
strongly preferred.

## Regression test

No new assertion is needed for the dedup itself; the vendor's existing fixture
suite is the behaviour baseline, and the refactor must leave it byte-identical.
Record the full fixture run before and after — the point of doing this as a
separate change from
`issues/vendor-markdown-truncated-utf8-aliases-a-valid-link-label.md` is that
the dedup is provably behaviour-preserving and the truncation fix is provably
not.

This is the last surviving item of that row. The six non-vendor sites it lists
(`std/imm/string.yo`, `std/regex/{parser,index,vm}.yo`, `std/string/string.yo`,

whole row as remaining.
